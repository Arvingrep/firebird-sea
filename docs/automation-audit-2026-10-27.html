六、这次审计挖出的真实缺陷

按优先级

不是清理问题，是会咬人的问题。建议按顺序修。

  1. P0派单链硬编码 canary 域名：tg_dispatch_courier_flow 的 8 个 HTTP 节点全写死 canary.fbird.men，生产 manila 的订单永远进不了抢单池。这是上线前必须改的。
  2. P0骑手桥 webhook 没有鉴权：fb-courier-bridge 节点未配 authentication（同项目的 agent-event 节点用了 headerAuth），任何人都能伪造 Telegram update 冒充任意骑手绑定。
  3. P0n8n 静态数据存在被覆盖风险：绑定表与回调 token 存在 n8n staticData，而仓库里 n8nac-config.json 配了 requireSyncBack，一次 push 就能把线上 token 覆盖成空串，/reg 全挂。
  4. P1verify-task.sh 静默丢覆盖率：:63 列着已删的 scripts/bmad/*、:94 依赖不存在的 test-api-db.sh，两处都被 || continue 吞掉，DB 集成测试其实从没跑过。
  5. P1lib.sh 的 bmad_stage 已断：7 处调用每次都失败，只留日志噪声。删函数 + 删调用点即可。
  6. P1k8s-mail-server.yaml 明文凭据：TG bot token 与 SMTP 密码直接写在入库的 yaml 里，建议改 Secret + 轮换。
  7. P1资讯供料的挂载不在版本控制：news_sync_schedule 从 n8n 容器内 require('/news-sync/...')，这个挂载没写进 GitOps，换镜像就断。
  8. P2README 与看板文档断链：README 仍教 make agent-dev（target 已删），BACKLOG.md 仍称由 dispatch-task.js 自动维护。
  9. P2生成器与 JSON 双源漂移：gen_tg_dispatch_courier_flow.py 生成同一份工作流，改 JSON 不改 py 就会在下一次生成时被覆盖。
  10. P2local-accept 在干净 macOS 上会假红：checks 第 13 行用 md5sum，缺 md5 -q 兜底。
