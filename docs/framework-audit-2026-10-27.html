一、先处理这个：凭据已经躺在仓库里

不是框架问题，是安全问题。以下三条都在 deploy/k8s-mail-server.yaml，该文件已入库、正在 default 命名空间运行、且不在 ArgoCD 管理下。

Telegram bot token 明文暴露

:276 把 TELEGRAM_BOT_TOKEN 以明文写在 YAML 里（8865562503:AAG…）。任何有仓库读权限的人都能接管这个 bot、读它的全部消息历史。

更麻烦的是：门禁抓不到它。 scripts/agent/gates.sh:112 的密钥扫描只检查 diff 的新增行——已经入库的密钥永远扫不到。这道门禁给你的是虚假安全感。

轮换 Telegram bot token立即
k8s-mail-server.yaml:276 · 找 @BotFather 执行 /revoke 重新签发，然后改成 Secret 引用。轮换前这串 token 视为已泄露。
轮换 SMTP 密码 + TLS 私钥立即
:28-55 是完整的 -----BEGIN PRIVATE KEY----- RSA 私钥；:67 与 :282 是明文密码 FbirdMail2026!。私钥泄露意味着 TLS 可被中间人。
修 fail-open 认证逻辑立即
:126 与 :141 写的是 pass === VALID_PASS || !VALID_PASS ——SMTP_PASS 为空时任意密码都能通过认证。这是一个可以被人随便用的开放中继。
把邮件服务收进 GitOps本周
它在跑，但不在 ArgoCD 里 → selfHeal 不回滚它、没有审计记录、和 RULES.md:68-71 自己定的「一切以 Git 为准」直接矛盾。要么进 Helm chart 加 mailRelay.enabled，要么建独立 ArgoCD Application。
密钥门禁改成全仓扫描本周
gates.sh:112 只看 diff 新增行，且正则不含裸 Telegram token 与通用 password:。存量密钥永远查不出——正是它漏掉了上面那条 token。
