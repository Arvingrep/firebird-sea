# `docs/agent/` —— 规则真相源与三把尺

> 这个目录只放**声明面**：规则写在哪、由谁证明。
> 门禁本体在 `scripts/agent/gates.sh`，叙述版手册在 `docs/internal/AGENT_PIPELINE.md`，都不在这里。

## 为什么需要这个目录

这个仓库的病不是「文档不够多」，是**同一条规则在三个面上长得不一样**：

| 面 | 长什么样 | 谁在看 |
| :--- | :--- | :--- |
| 声明面 | 文档里写着「必须 X」 | 人读 |
| 执行面 | `gates.sh` 的某个检查项在拦 | 机器跑 |
| 权限面 | `.claude/settings.local.json` / 分支保护放不放行 | 工具生效 |

三个面之间原本没有任何联动，所以每轮整理都在声明面加内容，执行面没跟上，权限面甚至反向。
**越理越乱的机制就在这里**，不是人不够勤。

`rules.yaml` 的作用是把三个面钉在一起：每条 hard 规则必须写出「谁在拦」和「谁证明它拦得住」，
两个锚点都要能被脚本解析到真实存在的那一行，否则体检红。

## 目录内容

| 文件 | 干什么 | 跑法 |
| :--- | :--- | :--- |
| `rules.yaml` | 规则唯一真相源。16 条 hard + 1 条 soft | `make rules` |
| `../scripts/agent/check-rings.js` | 四环体检 + 门禁项背书 + 出处锚点 | `make rules` |
| `../scripts/agent/spec-lint.sh` | 规范面自洽 8 项（内链/幽灵引用/基线/权限/死引用…） | `make lint` |
| `../scripts/agent/check-anchors.js` | 手册里指向执行面的锚点还准不准 | `make anchors` |

三个都**只读**：不写文件、不改 git 状态、不看 diff，可以随便重复跑。合起来一条命令：

```bash
make check-rules
```

## 四环：一条规则要活过三个月，四个环缺一不可

1. **产生** —— 写进 `rules.yaml`（有 ID、level、一句话规则）
2. **执行** —— `enforce: 文件#签名`，指向真的会拦的那一行
3. **检查** —— `test: 文件#用例名`，一条**故意违反 → 指定检查项 FAIL** 的用例
4. **收口** —— `.agent-runs/` 里的终态文件（`spec-lint.sh` S5 只能验「有没有」，验不了「真不真」）

第 3 环最容易糊弄过去：只断言「退出码是 1」是不够的——别的检查项也会让退出码变 1。
所以用例要用 `row_is "<用例名>" "<检查项名>" <期望rc> <期望标记>`，同时断「哪个检查项」和「什么结果」，
否则就是**假红顶真绿**：用例绿了，规则其实没人拦。

## 加一条规则的正确顺序

```bash
# 1. 先确认机器上真的有这个检查项
grep -n 'row "' scripts/agent/gates.sh

# 2. 写进 rules.yaml（enforce 用检查项名，test 用用例名）
# 3. 在 scripts/test-gates.sh 加：故意违反 → row_is 断指定检查项 FAIL
# 4. 体检
make rules          # 四环必须 100%，且「无背书 0」
bash scripts/test-gates.sh
```

只做第 2 步不做第 3 步 → 体检报 `NO_TEST`，规则降级为「写在纸上」。
只做第 1 步不加规则 → 体检报「门禁项无背书」：门禁在白拦，坏了没人知道为什么它存在，
误伤了也找不到该改哪条规则。

## 锚点为什么不用行号

行号是**位置的坐标**，文件一改，全部指针静默失效——不报错、不断链、CI 全绿，文档看着仍然完整。
本仓库早期 `AGENT_PIPELINE.md` 的 18 个 `文件:行号` 锚点实测 8 个错位，偏移集中在 +6~+8，
零症状，直到有人去核对才发现。

签名是**内容的坐标**：`gates.sh#无调试残留` 指的是「那一行检查项」，它挪到第 50 行还是第 500 行都无所谓。

同一类错误在这套工具自己身上犯过三次，都记在脚本注释里：

1. `check-anchors.js` 把文档名写死成小写 `agent-pipeline.md`，而仓库里是 `AGENT_PIPELINE.md`
   → **整份文档被跳过**，不是检查失败，是检查没跑。
2. `check-rings.js` 的门禁项背书把 `row "$1"` 的形参当成检查项名，造出「`$1` 无背书」的假阳性。
3. 诊断脚本用 `grep "tma\|vue"`（BRE 的 `\|` 在 BSD grep 上不可靠）得出「依赖已清理」的假阴性，
   差点把「没查见」写成「已还清」。

**结论：检查工具自己是这套体系里最危险的假信号源**，因为它出错时看起来像「查过了，没问题」。

## 这套东西不做的事（边界，别指望它）

| 不做 | 为什么 | 现在靠什么 |
| :--- | :--- | :--- |
| 判断规则**对不对** | 它只验「写的东西存在不存在」，不验「这条规则合不合理」 | 人读 + 独立 QA |
| 度量**误伤率** | 误伤是「门禁拦了不该拦的」，需要人反馈才知道，脚本看不到 | 只有代理指标（WARN 密度、绕过率） |
| 审计**中间产物** | `.agent-runs/` 未入库，草稿泄漏（draft leakage）无从查 | 暂无，属已知缺口 |
| 当**安全边界** | `AGENT_GH_TOKEN` 是 owner 本人的 PAT，agent 能建 `owner/*` 分支、能给自己打标签 | 真正的隔离只有 GitHub Environment 审批 / 凭证分离 |

最后一条尤其重要：`owner/` 通道的价值不是「把门禁变安全」，是**把绕过换成留痕**——
在此之前，改不动护栏的人只有一条路：直推 canary，连 PR 都没有。
