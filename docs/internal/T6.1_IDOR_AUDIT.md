## 1. 五个归属敏感接口的覆盖结论

T1.3 列出的五个接口为 `orderDetail`、`cancelOrder`、`operAddress`、`delAddress`、`getMemberAddress`。
逐个核对 A/B 会员越权测试如下（行号对应本 PR 合并后的 `fb-proxy-ownership.test.js`）：

| 接口 | A/B 越权测试 | 行号 | 断言内容 | 结论 |
|---|---|---|---|---|
| `orderDetail` | 有 | `:103` | A 持 B 的 `id=20` → **断言 `status === 404`**，且响应体不含 `OB-secret`；对照组自己的订单 200 | 覆盖 |
| `cancelOrder` | 有 | `:111` | A 取消 B 的 `id=20` → **断言 `status === 404`**，`orders[20].state` 仍为 0，`mutations` 为空 | 覆盖 |
| `delAddress` | 有 | `:119` | A 删除 B 的 `id=2` → **断言 `status === 404`**，上游从未收到 `delAddress` 请求，B 的行仍存在 | 覆盖 |
| `operAddress` | 有 | `:127` | A 编辑 B 的 `id=2` → **断言 `status === 404`**，无任何写入，`addresses[2].person` 仍为 `B-secret` | 覆盖 |

## 2. `getMemberAddress` 为何不是 404 测试（不需要 404 的理由）

这是五个接口里唯一不以 404 收尾的用例，理由如下，不是跳过：

`getMemberAddress` 在上游的实现（`waimai.class.php:1931`）是 ``WHERE `uid` = $uid`` 的**列表查询，不接受
对象 ID**；`$uid` 取自会话（`$userLogin->getMemberID()`）。因此它**不存在"用 B 的对象 ID 请求"这一攻击面**
——没有 ID 可以替换，也就没有可被拒绝的对象。

它真实的越权面是**参数透传**：若客户端自带的 `userid`/`uid` 被转发到上游，查询范围就会被改写。
所以正确的断言形态是"参数不透传 + 返回集合里没有 B 的数据"，`:135` 的用例正是如此断言的
（`sent.userid === undefined`、`sent.uid === undefined`、`sent.id === undefined`）。
白名单侧对应 `fbProxy.js:21`，`params` 仅允许 `cityid/gettype/lat/lng/shopid`。

结论：该接口以 404 为断言在语义上不成立，当前形态是正确的覆盖，**不需要补 404 测试**。

## 3. 本次补充的两个用例（原覆盖的真实盲区）

五个接口虽均有覆盖，但核查中发现两处**测试盲区**，已在同一文件按现有风格补上。两者都经过
变异测试（mutation testing）验证非空跑，详见 §4。

### 3.1 交叉传输面（`:149`）

原有五个用例中，每个接口的 `id` 只走了**一条**传输通道：`orderDetail`/`cancelOrder`/`delAddress` 走
query，`operAddress` 走 POST body。而 `fbProxy.js:132` 的合并逻辑是
`merged = method === 'POST' ? { ...query, ...body } : query`——归属判定不应依赖 `id` 从哪一侧进来。

补充用例让每个接口改走**另一侧**通道（前三者改 POST body、`operAddress` 改 query），断言仍为 404、
无数据泄漏、无写入、B 的订单与地址不变。

### 3.2 归属预检被跳过时的兜底（`:172`）

`fbProxy.js:201` 的预检是**条件式**的：

```js
if (rule.ownershipPrecheck && clientParams[rule.ownershipPrecheck.idParam]) {
```

而 `sanitizeParams`（`fbProxy.js:68`）会丢弃数组值（`typeof v !== 'string'`）以及不在 `params` 白名单里的
大小写变体（如 `ID`）。两者叠加的后果是：**`id` 被净化丢弃时预检静默跳过，写操作仍然转发上游**。

静态复核结论：**当前不构成可利用的 IDOR**。因为 `id` 丢失后退化为"不带 id"，而非"带着 B 的 id 透传"，
上游 `operAddress`/`delAddress` 的 SQL 仍有 ``AND `uid` = $uid`` 收口（`waimai.class.php:2074`、`:2192`）。
但这是个**脆弱不变量**——未来若有白名单条目的"缺省 id"语义是"全部"，同一条代码路径就会变成真实越权。

补充用例用数组值与大小写变体两种方式触发该路径，断言 B 的订单/地址行完全未被触及，且上游**从未**
收到 `id=2` 或 `id=20`。

## 4. 新增用例的有效性验证（变异测试）

为确认补充的不是"永远会过"的假测试，对 `fbProxy.js` 注入两个回归后重跑（注入仅在本地临时进行，
已还原，PR 中 `fbProxy.js` 无改动）：

| 注入的回归 | 结果 |
|---|---|
| 预检改读原始 `query` 而非净化后的 `clientParams` | 17 个用例中 **3 个失败**（含两个新增用例） |
| `sanitizeParams` 放行数组值 | **仅 §3.2 的新增用例失败**，原有 15 个用例全部通过 |

第二项是关键证据：该回归**被且仅被**新增用例捕获，证明它确实补上了原有测试集的盲区。

## 5. 一并确认的既有防护（非 T1.3 五接口，但属同一门槛）

- **骑手 Cookie 旁路**：`waimai.class.php:6063` 在 `userid == -1 && did > -1` 时 SQL 退化为
  ``WHERE `id` = $id``，**无归属过滤**——持任意 `courier` Cookie 可读任意订单详情。代理侧的缓解是
  从不转发客户端 Cookie，由 `:219`（行为）与 `:238`（源码防回归）两个用例锁住。
- `orderDetail`/`cancelOrder` 的 `$userid`/`$uid` 均取自 `$userLogin->getMemberID()`
  （`:6017`、`:4973`），为会话派生而非请求参数，已核实无参数后门。
- `article:orderDetail` 无登录校验，明确不在白名单（`fbProxy.js:20` 注释）。

就本次审计范围（静态 + 自动化测试覆盖）而言，T1.3 的五个接口**均有真实的归属校验测试，均可进入
白名单**，未发现「不得进入白名单」的接口。
